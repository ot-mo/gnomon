# Tools

Node scripts for checking the game, and the browser scripts that drive it in headless Chromium. The Node ones need
**Node 20 or newer** and nothing else: no npm packages (0D2 ran them on Node 20.11.0). The `package.json` at the
repository root only declares `"type": "module"`, so Node loads `src/*.js` as ES modules.

## Running everything

**Every check, in Node:**

```
node tools/run-all.mjs            (or: --only golden,zones; --jobs n, default one per CPU but one)
```

It runs every `check-*.mjs` in this folder, each in its own Node process, side by side, and exits non-zero if any
fails. The checks that hold a time budget (`check-dungeons`, `check-status`, `check-stats`, which replays
`check-status`, and `check-perf`) run afterwards, alone, so the others can't slow them down. At the end of 0D2: 37
checks, about 115-125 s with 11 at a time (an i7-10750H). On a
machine busy with other work a timed check can fail on time alone: run the last tag's tree in the same conditions
before believing it (`check-perf` does that itself; see its row).

**One check:** `node tools/check-<name>.mjs [options]` (the options are in its row below), or
`node tools/run-check.mjs <name>[,<name>…] | --all [options]`, which runs check modules through their `run(env)`, the
way the browser does. The check logic lives in `tests/checks/*.js` as functions returning
`{ name, ok, problems, stats, notes? }`; `tests/checks/index.js` lists every check module (one line each, with its
Phase 1 owner and its `slow` or `node` mark), and each exports `run(env)`, which takes its inputs from an environment
both Node and the browser give (described at the top of that file; `node-check-env.mjs` in Node,
`tests/lib/browser-env.js` in the page). A new check is `tests/checks/<name>.js`, `tools/check-<name>.mjs` (which
`run-all` picks up) and its line in the index.

**The browser scripts** (`browser-*.mjs`) need Playwright, which the repository doesn't depend on, so `run-all`
doesn't run them. Install it once, globally (`npm i -g playwright`, then `npx playwright install chromium`), and point
Node at the global modules:

```
Git Bash:     NODE_PATH="$(npm root -g)" node tools/browser-0d2.mjs
PowerShell:   $env:NODE_PATH = (npm root -g); node tools/browser-0d2.mjs
```

They launch headless Chromium with no options. `browser-gate`, `browser-silent`, `browser-0d1` and `browser-0d2` serve
the repository themselves; `browser-shell` and `browser-0c` need a server already running from the repository's root
(`node tools/serve.mjs 8642`, then `--port 8642`; `browser-0d2 --base http://127.0.0.1:8642` can use one too). Stop the
server afterwards. (`python -m http.server 8642` serves the same files, but on Windows it refuses part of the ~150
module requests a boot makes at once: about one boot in five stalls on `net::ERR_CONNECTION_REFUSED`, and a burst of
every `src/` module at once lost 470 of 1,570 requests to it and none to `tools/serve.mjs`, 0D2's verification.)
Every browser script opens the game with `?silent=1` and also installs, before any page script, an init script that
sends anything connected to the speakers into an `AnalyserNode` followed by a zero-gain node: **audio never reaches
the speakers**. They close the browser when they finish.

**Playing it, or poking at it, by hand:** serve the repository's root (`node tools/serve.mjs`, port 8130; the `gnomon`
preview configuration in the local `.claude/launch.json` runs the same, as DECISIONS says) and open
`http://127.0.0.1:8130/index.html` with any of these flags (`src/config.js` `FLAGS`):

| Flag | What it does |
|---|---|
| `?silent=1` | Everything bound for the speakers goes into an `AnalyserNode` followed by a zero-gain node (`audio.js` `audioOut`): the game makes its sounds and nothing is heard. Use it for every automated or headless run. |
| `?quick=1` | Skips the title screen: straight into a new quick game (the intro pages first). Without it the page opens on the title (New quick game / Continue). |
| `?seed=N` | The run's seed (a whole number above 0) for a quick game or "New quick game"; without it, a random one. |
| `?debug=1` | Reserved for the debug overlays Phase 1 adds (`FLAGS.debug`; nothing reads it yet). The console's `window.game` and `game.debug` (`step`, `draw`, `enterZone`, `mapKey`…) work without it. |

For example `index.html?silent=1&quick=1&seed=1234&debug=1`. Close the tab when you are done: a hidden pane keeps
running, and so would the music.

**The checks in the browser:** `test-world.html` (0D2) runs the check modules of `tests/checks/index.js`, each in an
iframe of its own (`?check=<name>`, as `run-all` gives each its own process), with a summary and `window.testResult`
(`{ ok, passed, failed, skipped, results, secs }`). It leaves out the Node-only ones (`perf`, `save`, `stats`) and,
unless asked for with `?all=1` or `?only=a,b`, the slow ones (`edges`, the longest at about 40 s, and `dungeons`, held
to a p95 time budget); any other option passes on to the checks (`?seeds=10`). At the end of 0D2 the default set (32)
passed in 62 s headless, all 34 in 112 s. A check page gets no `AudioContext` (so no sound, and no sound effect draws
from a seeded `Math.random`, as in Node) and an in-memory `localStorage` (`tests/lib/browser-env.js`). `test.html`
runs the dungeon validation (1,000 legacy floors) and the art checks in the browser (`window.testResult`);
`check-dungeons` and `check-content` do the same in Node.

## Re-recording the golden fixtures

The fixtures were recorded once, before any game code changed, and every later check compares against them. Never
re-record them to make a check pass: when an API changes, update `tests/golden/current-api.js` instead. To record them
again from the parent's code (for instance to confirm they are right):

```
git archive 75edbd3 src | tar -x -C <tmp>
copy package.json <tmp>\           (any package.json with "type": "module" above src/)
node tools/golden-record.mjs --src <tmp>/src --out <tmp>/golden
```

and compare `<tmp>/golden/*.json` with `tests/fixtures/golden/*.json`. They match byte for byte (line endings aside).

What the fixtures contain is described at the top of `tests/golden/scenarios.js`. Renamings the adapter
makes (never the fixtures): the parent's `gold` field is `currency.funds(p)`, and the `cash` piles generation lays
today are shown under the parent's kind name `gold` (the same pile); the five gear fields are read from the body. They were recorded in Node 20; compare
them in Node (the renderer uses `Math.exp` and friends, whose last bits are not promised to match in other engines;
Chromium shares Node's V8, and `browser-0d1.mjs` finds the 27 frames identical there).
